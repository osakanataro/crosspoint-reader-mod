# CrossPoint Reader OST 改造版

XTEINK X3上で日本語EPUBファイルを読むために、CrossPoint Reader を改造しています。
命名は面倒くさくなったのでOSakanaTaro版ってことでOST版です。

### 開発支援機構

シリアルコンソールの使えない端末で、遅さや不具合を主観ではなく数値で扱うための仕組み。
縦書きの不具合の多くは「コンパイルは通るが表示が壊れる」種類なので、実機から測って
持ち帰る手段が無いと原因の特定が推測合戦になる。

#### 診断基盤（INPUT_DIAG）の実装


- 目的: 動作の遅さや不具合を「体感で遅い」という主観の表現で扱うのではなく、
  ページめくりの所要ミリ秒やヒープ残量といった実測値として定量的に記録し、
  修正前後の比較や原因の切り分けを数値で行えるようにするため作成
- シリアルコンソールが使えないX3向けの、SDカードへ書き出す入力・描画計測
  （`/input-diag.txt`、`src/util/InputDiag.*`、`-diag`ビルド命名の`scripts/ost_version.py`）
- 1.6系開発時に追加: プリウォーム経路の計測（`page_scan_last`/`prewarm_entry_fails`）と、
  本を開く6段階のヒープ記録（`/open-heap.txt`。クラッシュしても直前までの段階が残る）
- 2026-09-03追加: **ビルド番号を診断ファイルとクラッシュ報告の先頭に出す**
  （`build=2026090305-diag` / `OST build: 2026090305-diag`）。`CROSSPOINT_VERSION`はコミットまでしか
  区別できず、未コミットの変更を積んだ試験ビルドは全部同じ文字列になる。実際に引き金の無いビルドを
  試験して1本無駄にしたのが動機。`scripts/ost_version.py`がビルドごとに`lib/hal/ostBuildId.generated.h`
  を書き、読むのは`HalSystem.cpp`と`InputDiag.cpp`の2ファイルだけ（定義にすると全ファイル再コンパイルになる）

#### 描画が返らなくなったときの自動再起動（開発ビルド専用、`DEBUG_RENDER_WATCHDOG`）


- 動機: 描画タスクが戻らなくなると端末を復帰させる手段が無い。描画タスクはどのウォッチドッグにも
  登録されておらず、CPU0のアイドルタスクも監視対象外（`sdkconfig.default`で
  `CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0`が未設定）、電源断の判断は止まった描画に
  食われている`loop()`側にある。リセットボタンは接着された画面の下にあって押せない。
  結果として電池を空にするしか手が無く、それに1日以上かかる
- 対策: 描画の間だけ描画タスクをタスクウォッチドッグに登録し、30秒返らなければパニック再起動させる。
  待機中（通知待ち）は登録しないので、何もしていない端末で発火することはない。
  監視区間には描画ロックの待ちも含まれる——既に固まった描画が握っているのがそのロックだから
- 30秒という緩さは意図的で、「遅い」と「返らない」を区別できれば十分。実測の最大は時計の初回描画
  3.2秒、低速描画記録に残る最大が画像混在ページの5.6秒
- 旧ツリー（`develop`/`feat/vertical-writing-foundation`）の`c8318eae`を`feat/vertical-1.6`へ移植したもの。
  **2026-08-27に時計モードが約19分でハングして放電待ちになった直接の原因は、フラグを渡していても
  このブランチに実装自体が載っていなかったこと**——`#ifdef`なのでエラーも警告も出ずに素通りしていた
- 実機検証（2026-08-28〜29、下の電池測定と同一セッション）: 9時間16分・描画567回で誤発火ゼロ、
  uptime連続を確認

#### ビルド時間の修正（無変更の再ビルド 188秒→20秒）


- ビルド番号（OST_VERSION）を毎ビルド、コンパイル定義として全翻訳単位に注入していたため、
  番号が進むたびに全オブジェクトが無効化され、何も変えない再ビルドでも
  ライブラリ込みの全再コンパイル（188秒・CPU10分）になっていた
- このマクロを読む場所はどこにも無かった（dist/のファイル名だけが番号の使い先）。
  注入をやめて解消。副産物としてビルドが決定的になった（同じソースからバイト同一のバイナリ）

### 縦書き実装

本家に縦書きが無いため、このforkの主目的。組版そのものと、それを日本語フォントと
商業EPUBのCSSを積んだ状態のメモリで動かすための対策が半々になっている。

#### 電書連 EPUB 3 制作ガイド準拠CSS サポートのためのメモリ管理

出版社の制作ガイドに沿ったEPUBはスタイルシートが大きく（実測144KB・約1,865ルール）、
これを読み込むだけでヒープを使い切る。読めないのではなく、読むと落ちる・読んでも
効かないという形で表面化し、原因の特定に何度もかかった領域。

##### 電書連 EPUB 3 制作ガイド準拠CSSによるメモリ枯渇の解消（JP版 #103/#105/#106 の移植）


- 電書連 EPUB 3 制作ガイド準拠CSS（実測144KB・約1,865ルール）が構築時に丸ごとRAM展開されて
  ヒープを食い尽くし、`-fno-exceptions`下の`bad_alloc`→`abort()`で再起動する問題への対策
- `CssSelectorUsage`: 章のHTMLを走査して使用タグ/クラス集合を作り、マッチするルールだけを
  RAMにロード。`Epub::load`のキャッシュ検証もヘッダのみの`validateCache()`に変更
- CSSパース中の32KBヒープガード3箇所と、打ち切られた不完全ルール集合をキャッシュに
  保存しない対策（オリジナルはJP版 zrn-ns氏）
- 効果（実測）: 構築の消費 約95KB→約24KB、読書中の空きヒープ 15KB→74〜90KB、クラッシュ解消

##### 巨大なCSSを持つ商業書籍でスタイルが全く効かない問題の解消（2026-08-31、実機検証済み）


- **症状**: 電書連＋角川テンプレートを積んだ商業書籍（CSS6ファイル・3,172ルール）で、
  挿絵の寸法指定が効かない。調べると`.fit`にすら上限が付いておらず、
  **その本のCSSが1件も適用されていなかった**
- **連鎖の構造**（診断で確定）: 一つ一つは妥当な判断が積み重なって最悪の結果を生んでいた
  ```
  css trunc#2 at 274 rules  free=32576   ← 解析がヒープ枯渇で3ファイル目の途中で打ち切り
  css skip#3/#4/#5 need=65536            ← 残り3ファイルは着手すらできない
  css done rules=274 complete=0          ← 未完了なのでキャッシュに保存しない
  fit ... rules=0                        ← 章の構築時、キャッシュ読みが失敗して
                                            その274件も消える
  ```
  つまり**CSSが大きい本ほどスタイルが効かず、ある大きさを超えると全く効かない**
- **対策**: `loadFromCache`が従来から使っていた「章が参照しうるルールだけ読む」絞り込みを、
  キャッシュが無いときの**解析時にも適用**する（`CssParser::setUsageFilter`、
  `Epub::parseCssFilesFiltered`）。ヒープが埋まる前に必要なものだけ登録するので打ち切られない
  - 実測: 上記の章で**3,172ルール中7件だけを登録、complete=1、空き83KB**。
    挿絵はmax-height 10%/20%/80%が効いて 166x180→70x76、195x316→93x151、
    199x1345→89x605 と著者指定どおりに描画された
  - 絞り込んだ結果は**キャッシュに保存しない**——1章分の視界なので、他章が読み戻すと
    必要なルールを失うため
- **診断の追加**: どのファイルを何故飛ばしたか、各ファイルが何件寄与したか、どこで打ち切られたか、
  最終ルール数と完了フラグを`/image-diag.txt`に記録。**この不具合について机上で立てた8つの仮説は
  全てコード上は正しく、全て外れた**（`auto`の解釈・セレクタ形式・コメント除去・ルール数上限・
  クラス収集・クラス分割・ヒープ閾値・キャッシュ版数）。診断を入れた最初の1回で確定した

##### メモリ断片化・クラッシュ対策


- グリフ用アドバンステーブルの収集バッファを16KB一括確保から256件開始の倍々成長に変更
  （断片化ヒープでの章ジャンプ7〜12秒/クラッシュの原因だった）
- グリフビットマップのミニアリーナを4KBチャンク分割確保に変更
  （本家未マージの`feat-chunk-bitmaps`由来。最大連続5KBの環境でもプリウォームが成立する）
- リスト画面（章選択・ブックマーク等）を開いた時点で全SDフォントキャッシュを解放
  （読書フォントの常駐数十KBを返してから章ジャンプの構築が走る）
- ページ読み込み前の低ヒープガード: ビルド進行中に空き20KB未満なら`suspendBuild()`で
  構築を部分ファイルとして退避（既存の遅延再開機構が引き継ぐ）、12KB未満でフォントキャッシュ解放

##### 章を開けなくなる「Failed to index」の対策（実機確認済み）


- 実機ログで原因を特定: 章本文をzipから取り出すには約32KBの連続した空きメモリが要るが、
  ルビや珍しい漢字の多い本を読み進めると空きが細切れになり、合計では足りていても
  連続では取れず3回連続で失敗→「Failed to index」になっていた。既存の保護は
  空き合計しか見ておらず、この断片化を見逃していた
- 章本文の取り出し直前と再試行時に「最大連続48KB未満ならフォントの確保済み領域を
  返してから実行」する保護を追加。再現していた本で全章のページ送りが通ることを確認

##### 同一起動内で本を開き直すとメモリ不足で落ちる問題の対策（実機確認済み）


- 読書フォントのキャッシュは本を閉じても保持される設計のため、同じ電源投入中に
  本を開いて閉じて別の本を開くと、2冊目は初回より約60KB不利な状態から始まる。
  CSSの重い本＋アンチエイリアスONの組み合わせでは足りなくなり、字形情報の確保が
  次々失敗（1KBの確保すら失敗）→ページ描画16秒→最終的に再起動、という実クラッシュが発生した
- 対策: 本を開く処理の冒頭で、空きが60KB未満（または最大連続40KB未満）なら
  フォントキャッシュを返してから開くようにした。開き直しが健全な初回と同じ条件になり、
  代償は開き直し直後1〜2ページの再読み込みのみ。クラッシュした再現手順で
  正常動作（空き72KBで開始・通常速度・クラッシュなし）を実機確認
- あわせて「本を閉じた時にどれだけメモリが戻ったか」の計測を診断に追加。初計測で
  「閉じて戻るのは約1KBだけ＝開くコストのほぼ全てはフォントキャッシュと固定インフラ」
  という実態も判明した

##### 断片化ヒープへのガード2件と診断強化（クラッシュ2件の解析から、実機検証済み）


- test_vertical_ja.epub（縦書き・フルCSS・AA ON）の長時間セッションで2回クラッシュ。
  スタック解決で原因を特定した:
  1. **メニュー起動が素の`new`でabort**——読書中の空きが枯れた状態でメニューボタンを押すと、
     メニュー画面の生成が`bad_alloc`で落ちる（枯渇時に次に確保した者が死ぬ既知の系統）
  2. **開発用の描画見張り（30秒）の誤射**——断片化で字形常駐が組めず、1描画2362文字を
     SDから約10ms/字で読み進む「生きているが遅い」描画が28〜30秒に達し、
     見張りがハングと誤認してパニック再起動させた
- 対策: (a)メニュー起動前に最大連続16KB未満でフォントキャッシュ解放、生成失敗時は
  その押下を無視して読書続行（abortしない）。(b)ページ読み込み前のガードに
  **最大連続ブロックの条件（24KB）を追加**——従来は空き合計しか見ておらず、
  「合計51KB空きで最大連続16KB」という断片化の崩落を素通りしていた
  （2026-08-22の章構築側と同じ穴のページ送り側）。(c)見張りには字形のオンデマンド読みを
  「前進の証拠」として報告し、閾値の意味を「30秒で終わらない」から「30秒間何も前進しない」に変更
- 診断: 起動時に前セッションの`/input-diag.txt`を`/input-diag.prev.txt`へ退避。
  クラッシュ後も死に至るまでのヒープ推移（render_logの系列）が残る——今回の
  「最大連続37KB→16KBの崩落」はこの退避が初出動で捕らえたもの
- 修正後の実測: 同書を全編通読成功。最悪描画 28,046ms→5,368ms、1描画のオンデマンド読み
  2,362→205、読書中の最大連続27〜43KBを維持。AA用の作業領域が瞬間的に取れなかった
  1ページは既存のフォールバックがAAを諦めて白黒で完走（4.3秒）

#### CSSの装飾が本によって出たり出なかったりする問題の解消（2026-09-02、実機検証済み）
`resolveStyle`（クラスから文字の装飾を引き当てる処理）に**空きヒープ48KB未満なら空の
スタイルを返す**判定が入っていた。この関数は**何も確保しない**——結果はスタック上の
構造体（列挙型・長さ・ビットフィールドのみ）、規則表は引くだけ、クラス走査は
`string_view`。CSSを丸ごとRAMに展開していた頃の名残で、章ごとの絞り込みを入れて
確保が無くなったあとも閾値だけが残っていた。

**48KBはこの機種の読書中の空き（47〜63KB）のただ中**にあり、通常のページで跨ぐ。
症状は「同じ本の同じ章で、前半の段落は装飾が効き後半は効かない」「開き直すと結果が

#### 縦書きの下線・打ち消し線の実装（2026-09-02、実機検証済み）
装飾線を引く処理が横書き用の`render()`にしか無く、縦書きでは**CSSの解釈も文字への伝達も
正常なのに線だけが出ない**状態だった（診断で`td=1/1`を確認）。上のテストで見つかったもの。

縦書きでは線は列に沿って走る。**傍線は文字の右脇**（マスの外、列間の隙間）、**打ち消し線は
文字の中央**を縦に貫く。連続する範囲を1本にまとめる方式は横書きと同じで、座標の取り方だけが違う。

判断が要った点: 縦書きのルビは文字の右半マスに置かれるため、**ルビのある段落では傍線を左に**
引く（ルビが右半マスを占めるため。**JLREQに傍線の左右を定めた規定は無い**ので、衝突しない側を選んだ）。トークンの列方向の長さは、
横倒しの欧文列だけ実測、それ以外は1マス分——回転する括弧や縦中横は送り幅が1マスのため。

実測: 線は文字の右2px・隣列の文字から約13pxに入り、文字に触れない。範囲外へのはみ出しなし。
列をまたぐ範囲でも途切れない。

##### 傍点（圏点）の表示（実機検証済み＝テスト第10章合格）


- CSSの `text-emphasis` / `text-emphasis-style`（`-epub-`/`-webkit-` 付きも含む6綴り）を解釈し、
  胡麻点・白胡麻点・点・丸・白丸・三角・二重丸の各字形で傍点を描く
- 描画はルビと同じ経路に載せた。縦書きは1文字＝1マスなので1マスに1つの印がそのまま対応する。
  横書きは1単語が1つの塊なので、印の後ろに全角スペースを挟んで文字数と幅を合わせている
- 同じ範囲にルビと傍点の両方が指定されたときはルビが勝つ。子孫要素の `none` は祖先の指定を
  打ち消す（下線などの装飾とは逆の挙動で、CSS本来の仕様どおり）
- 胡麻点（﹅ ﹆）は読書フォントに収録が無いことがあるため、収録の有無を実測して
  無ければ点（• ◦）に置き換える。フォントを更新すれば自動で本来の字形に戻る
- **縦書きで連続する欧文は1つのマスにまとめて横倒しにするため、`ABC` のような並びには
  印が1つしか付かない**（`X3` のような縦中横も1マス＝1つ）。日本語の文字には1つずつ付く

##### 読書フォントに無いCJK互換漢字を統合漢字で描く（実機検証済み＝テスト第9章合格）


- 出版社の組版システムは字体を指定するためにCJK互換漢字（U+F900〜FAFF）を使うことがあるが、
  書体側にその字体が無いと豆腐になる。実際 BIZ UD系は 蓮 U+F999 は持つが
  溺 U+F9EC・煉 U+F993 を持たず、商業EPUB調査で見つけた3字のうち2字が表示できなかった
- 互換漢字と統合漢字は同じ字なので、読書フォントに字形が無いときだけ統合漢字の符号位置に
  置き換えて描くようにした。どちらもUTF-8で3バイトなので文字列をその場で書き換えられる。
  縦書き・横書きの共通経路に置いてあるため両方に効く
- 対応表は512要素の16bit配列（フラッシュ1KB、RAM消費なし）。有効なのは453字

#### 記号の縦書き向きをUAX#50の定義どおりにした（2026-09-02、実機検証済み）
記号の正立/回転を、規格（UAX#50）の`VerticalOrientation.txt`から vo=U の範囲を機械的に
抽出した46区間の表で判定するようにした。**どの記号が正立らしいかをこちらで判断していない。**
対象ブロックは両者が細かく混在しており（文字様記号だけで正立44字・回転36字）、ブロック単位では
扱えないため。

直った文字: **①②③などの丸数字**（日本語書籍で頻出）、ローマ数字ⅠⅡⅢ、℃ ℓ №、
⭐⬛⬜ ⌒ ⌘ ♥ ☆ ♪ ‼ ⁇⁈⁉ ● ○ ※ † ‰。いずれも横倒しになっていた。

**あわせて、それまでの記録の誤りを訂正する。**「矢印が横倒しになるのは実害あり」と
未対応一覧に書いていたが、規格に当たると**矢印はvo=R（回転）が正しい**。縦組みでは読み進む
向きが変わるため、横組みで右を指す矢印が下を指すのは意味の変化ではなく同じ意味の反映である。
当版の動作は最初から正しく、実際に困っていたのは丸数字のほうだった。規格を確認せずに書いた
観察がそのまま残件一覧に残っていた。ギリシャ文字・キリル文字・Å・℘も同じくvo=Rで回転が正しい。

テスト7の判定文も「原稿どおりの向きなら合格」から「列の流れに合わせて向きが変われば合格」へ
訂正し、丸数字とローマ数字の段落を追加した（使用する10字が3書体×2ウェイトで実グリフを持つことを
確認済み——「横倒し」と「未収録」を取り違えないため）。

向きの判定は描画時だけでなく**章キャッシュを作る時点**でも使う（正立なら1マス、回転なら
横倒しの欧文列に合流するので、列の折り返し位置そのものが変わる）。**SECTION_FILE_VERSION 48→49**で
既存キャッシュを作り直させている。

#### JLREQ・UAX#50との突き合わせ（2026-09-02）
規格2つと実装を項目ごとに照合した。UAX#50側は判定を機械的に再現して全符号位置で差分を取り、
JLREQ側は章立てに沿って実装の有無を確認している。

**UAX#50**: フォントが字形を持つ＝実際に見える不一致は解消した。追加で直したのは

#### CSSによる寸法指定への対応

##### 画像のmax-width/max-height対応と列はみ出しの解消（2026-08-31、実機検証済み）


- **max-width/max-heightがCSSパーサに存在しなかった**。`width`/`height`しか解釈しないため、
  上限指定のある画像はすべて「コンテナに収める」既定動作に落ち、40%指定と100%指定が
  同じ大きさで描かれていた。**955冊調査で「市販の縦書き本の挿絵はほぼ全てmax-*クラスで
  寸法指定、固定幅は皆無」と判明していた**のに実装が伴っておらず、つまり商業書籍の挿絵は
  一枚も著者の指定どおりに表示されていなかった
  - 解析・**CSSキャッシュへの往復**・寸法計算の3箇所に対応。当初は解析だけ実装して
    キャッシュの直列化を忘れ、指定が読み戻しで消えていた（`width`/`height`は往復に
    入っていたので効き、`max-`だけ効かない、という食い違いの正体）
  - `width`/`height`と違い**縮めるだけで拡大しない**ので、上限はコンテナに対する下限として
    適用する。上限より小さい画像は原寸のまま（実測: 240x160の画像はmw=512*でも240x160）
  - 実機実測: 同じ560x760の画像が max-100%で512x694、**max-40%で205x278**
  - SECTION_FILE_VERSION 48、CSS_CACHE_VERSION 11
- **空白を含まない長い欧文が列を突き抜ける問題を解消**。解析器は連続ASCIIを1トークンに
  まとめるが、横倒しトークンの列方向の高さは語の幅そのもの。列より長い1トークンは
  トークン間でしか分割できないため、列の先頭から下へ突き抜けてステータスバーを侵食していた
  （2026-08-29のdiagにある`!! Outside range`論理y=855の正体）。文字境界の分かる解析段階で
  列に収まる大きさに分割し、レイアウト側にも保険の分岐を置いた。等幅系とゴシック系で
  分割位置が変わることを実機確認——実測した文字送り幅で判定している証拠。SECTION_FILE_VERSION 47
- **診断の強化**: 画像1枚ごとに`fit mw=N* mh=N*`（星は著者が指定した上限）を記録。
  写真の見比べでは6往復しても決着しなかったmax-指定の可否が、この1行で確定した。
  あわせて画像診断のリングを24→48件に拡張（10枚の章で約50行書かれ、
  肝心の先頭が溢れて2回続けて必要な行が取れなかったため）

#### ページ送り速度の改善

##### 挿絵のあるページのページ送りを約4秒→約1.1秒に（2026-08-31、実機検証済み）


挿絵を含むページは、残像を消す「清書」の画面書き換え（3.2秒）が毎ページ走っていた。
原因は清書の予約の出し方で、挿絵ページを描くたびに「次のページで清書する」を無条件に
予約しており、**清書を実行してもその予約が解除されないまま次の挿絵ページでまた予約される**。
結果として設定した清書間隔が働かず、挿絵が続く章では実質毎ページが清書になっていた。
挿絵のないページとまったく同じ勘定（清書したら設定間隔に戻す／それ以外は1つ減らす）に
揃えて解消。実測は9ページ中、通常ページ7枚が1.0〜1.35秒、清書は1回（3.4秒）。
副次的に画面バッファの出入りが減り、読書後のHome画面の最大連続ブロックが11KB→31KBに回復した。

この調査で、残件として記録していた次の2点が**いずれも事実と違うことが判明したので取り消す**。
- 「滑らかな描画のパスごとに挿絵をSDから読み直している」——読み直しは**発生していない**。
  計測値は`img_slot=4/0 stream=0 sd=0ms`で、全パスがRAMスロットから描かれている
- 「滑らかな描画が4秒の一因」——濃淡2面の描画は**合計約150ミリ秒**でほぼ無視できる。
  4秒のほぼ全部が画面の書き換え時間だった

この2点を誤って記録したのは、診断の`gray_lsb`という数値を額面どおり読んだため。この区間には
画面書き換えの完了待ちが含まれており（挿絵のないページは書き換えを非同期で始めるため）、
1面目だけが2.2秒に見えていた。2面（同じ処理を2回する）を別々に計測する診断を足して確定した。

### 表示用フォントの作成

本家配信のフォントに日本語は入っていない（Latin/Greek/Cyrillicのみ）ため、元フォントから
自前で変換してSDカードに置く方式をとっている。リリースに `fonts-YYYYMMDD<連番>.zip` として添付。

#### 生成するフォントの仕様（OST版フォント fonts-YYYYMMDD<連番>.zip）


リリースに添付しているSDカード用日本語フォントは、`feat/japanese-sd-fonts`ブランチの
生成スクリプトで元フォントから自前変換したもの。BIZUDGothic / BIZUDMincho / NotoSansJP の
3書体×6サイズ（8/10ptはUI用、12〜18ptが読書用）、いずれもregular+boldの実体収録
（太字を斜め重ね打ちなどで合成せず、元フォントの太字から生成している）。
配置は `/fonts/<書体名>/<書体名>_<サイズ>.cpfont`。

#### フォントの選定基準


収録範囲は「日本語の書籍に実際に出てくる字を、元フォントに実在する字形だけで持つ」という
方針で策定している:

- **漢字はJIS X 0213で絞り込む**。CJK統合漢字ブロック（約2.1万字）を丸ごと収録すると、
  日本語の書籍にはまず出てこない簡体字などで容量と機器側の区間管理を圧迫する。
  日本の出版物の漢字はJIS X 0213（約1.4万字分の符号位置リスト）で実質すべて賄えるため、
  ブロック単位ではなく符号位置リストで選別する
- **JIS X 0213の記号行を漏らさない**。丸数字①〜㊿・㈱・㎝㎏などはUnicodeブロックとしては
  漢字と別の場所に散らばっており、漢字リストだけでは拾えない。実機で○数字が化けた実例を
  受けて、囲みCJK・CJK互換（単位）・漢文記号・アイヌ語表記用の小書きカナなどの
  ブロックを明示的に加えている
- **引用・理系表記に備えた文字を持つ**。JIS X 0208由来のギリシャ・キリル文字
  （ロシア語等の引用）、数学記号・矢印・罫線・幾何図形などの記号ブロック。
  元フォントに無い字（∼ ≈ など）はNoto Sans / Noto Sans Mathを後詰めにして補う
- **縦書き用句読点（U+FE10〜、2026-08-22追加）**。縦書きで「、。，」を正しい位置・字形で
  描くための文字。NotoSansJPは収録字形を直接、BIZ UD系はフォント内部の縦書き用代替字形を
  取り出して収録する
- **実在する字形だけを数える**。収録候補は必ず元フォントの対応表と突き合わせ、
  字形の無い符号位置は落とす（「範囲は宣言してあるが中身は空」という字を作らない）。
  なお機器側の制約で区間表は最大256区間に隙間統合されるため、区間表上の公称字数は
  実体より大きく見える（例: BIZ UD系は公称約2.1万字・実体約1.2万字）

参考として、同系統のYomuka版フォント（Yomuka版が配布する変換済みフォント集）と
収録範囲を実グリフベースで比較した（2026-08-23）。かな・JIS漢字・基本記号は完全に共通で、

| 分類 | 冊数 | 中央値 | 上位10% | 最大 |
|---|---|---|---|---|

| 大判 | 6 | 1452×2064 | 1748×2480 | 1748×2480 |

- **2048pxが事実上の上限**。これを超えるのは全体の1.0%しかない。長辺2048pxまでを設計上の

##### 固まり方をコード上で特定、周波数変更を直列化（2026-09-02、実機検証済み＝下2項）
上の「疑い」を追った結果、**2つのタスクが同時に`setCpuFrequencyMhz`へ入ると必ず止まる経路**が
Arduino基盤の中にあった:
- `setCpuFrequencyMhz`は変更の前後で登録先へ通知する。その通知は「周波数変更用の占有権」を
  取った中で呼ばれ（`esp32-hal-cpu.c:97-115`）、通知先のSPIは**変更前通知でSPIバスの占有権を
  取ったまま戻り、変更後通知で手放す**（`esp32-hal-spi.c:688-706`）
- タスクAが変更前通知を終えてSPI占有権を握ったまま本体の変更中に、タスクBが変更前通知に入ると、
  Bは周波数用占有権を握ったままSPI占有権を待ち、Aは変更後通知で周波数用占有権を待つ。
  **互いに相手の解放を待って永久に止まる**。どちらも時間切れの無い待ち
- 2タスクが同時に入る条件は`HalPowerManager`側にあった。`Lock()`は`currentLockMode`を
  `NormalSpeed`にした後、占有権を手放してから`setPowerSaving(false)`を呼ぶ。この間
  `isLowPower`はまだtrueなので、50ms毎に来るメインタスクの`setPowerSaving(true)`が
  第2分岐（`mode != None && isLowPower`）に入り、**メインタスクも160MHzへ上げようとする**。
  時計ではメインタスクが描画タスクを起こした直後に`main.cpp:734`へ来るので、同じ優先度の
  時間割で割り込まれるとちょうどこの窓に当たる
- 症状とも合う: 両タスクが待ち状態なので画面もBackも死に、CPUは空いているので割り込み監視は
  発火せず、タスク監視は購読が無かったので再起動もしない。窓は10MHzで走る`Lock()`内の
  数十〜数百μsで、機会は毎分1回。12時間持つことも1分で止まることもある頻度に見合う

直したのは`HalPowerManager::setPowerSaving()`で、モードの読み取りから`isLowPower`の更新まで
（`setCpuFrequencyMhz`本体を含めて）`modeMutex`の中に入れた。これで2タスクが同時に
`setCpuFrequencyMhz`へ入ることが無くなる。元の「負荷を避けるため占有権を使わない」という注記が
問題の根だった。コストはメインループ50ms毎の占有権取得1回。

あわせて調査用ビルドの監視を広げた（`DEBUG_RENDER_WATCHDOG`時のみ）:
- 時計モードの間だけメインタスクも30秒監視の対象に入れる（`ClockActivity::onEnter/onExit`）
- タスク監視の発火は`panic_abort`を経由しないため理由が空だった。`esp_task_wdt_isr_user_handler`
  を差し込み、止まっていたタスク名を`panicMessage`に残すようにした（`HalSystem.cpp`）
- 分の切り替わりと描画開始を`LOG_DBG("CLK", ...)`で残す。RTCメモリのログ環は再起動後も読める

調査用ビルド`2026090214-diag`以降、時計モードでの固まりは再現していない（下の一晩走行を含む）。
記録では分の切り替わりごとに「周波数を上げる」が**1回しか出ない**——直列化前は2タスクが同時に
入りうる形だったので狙いどおり。ただしこれは競合が起きなかった証拠であって、起こりえないことの
証拠ではない。

##### 監視の復帰経路を故意のハングで実証（2026-09-03、実機検証済み）
監視（番犬）が実際に発動したところを**一度も見ていなかった**。過去2回の固まりはどちらも監視の
無いビルドで、2026-08-27は「フラグを渡したのに実装がブランチに無く、黙って無効だった」失敗もある。
「30秒で再起動するはず」を仮定のままにしないため、`DEBUG_RENDER_WATCHDOG`のときだけ時計モードで
**故意にハングを起こす引き金**を付けた（`ClockActivity`）。監視対象の2タスクは登録場所が別なので、
1タスクにつき1つ:

| 押すボタン | 止まるもの | 実機での結果 |
|---|---|---|
| 前面のBack以外（Confirm/Left） | メインタスク（`loop()`内で`delay`の無限待ち） | 30秒で再起動、理由に`loopTask (CPU 0)` |
| 側面の2つ（Up/Down） | 描画タスク（`render()`内で同様） | 30秒で再起動、理由に`ActivityManager (CPU 0)`（`ActivityManagerRender`がFreeRTOSの15文字制限で切れたもの） |

Rightは除外——X3では電源ボタンとGPIO3を共有しており、電源操作で引き金が引かれると固まりと
区別がつかない。どちらも`delay(1000)`で待つのでCPUは回さず、**止まるのは監視への合図だけ**。
本物の固まりと同じ「タスクが応答を返さない」状態を作る。

確認できたこと: (1)メインタスクの監視登録が効いている（08-27に無効だった箇所）、(2)監視が30秒で
発火する、(3)本当に再起動する（ログが`[1]`から始まり直す）、(4)止まったタスク名が理由欄に残る
（`esp_task_wdt_isr_user_handler`の働き。無ければ空）、(5)SDに`crash_report.txt`が直前ログ付きで
書かれる。`clock-battery.txt`が`still running`で止まるのも、本物の固まり時に見えていた痕跡と一致した。
描画側の試験では**メインループが生き続けて`minute turn`を記録しながら描画だけ止まる**形になり、
実際に時計が固まったときと同じ形だった。**仮に本物の固まりが再発しても、失うのは1日分の電池ではなく30秒。**
