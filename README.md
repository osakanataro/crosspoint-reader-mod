# CrossPoint Reader OST 改造版

XTEINK X3上で日本語EPUBファイルを読むために、CrossPoint Reader を改造しています。
命名は面倒くさくなったのでOSakanaTaro版ってことでOST版です。

### 2026/08/20時点の開発方針
- XTEINK X3で動けばいい
  - aliexpressで買ったUSB接続ができないバージョンを使用
- Claude Codeで開発する
  - コンパイルなどはUbuntu 24.04仮想マシン上で実施
- 本家をベースにする
  - X3の最近のバージョンは液晶パネルが違う件への対応などが本家には入っているため
  - 2026/08/09から1.5.0ベースで開発開始。本家にXteink x4 pro対応が入ったあたりで乖離が始まった
  - 2026/08/20から1.6.0rcをベースにして再構成開始
- 日本語訳は付けない
- フォントはSDカード上に配置する
  - 容量食うのでSDカード上に置く
- ページめくりボタンは左が進むで、右が戻る
  - 縦書きフォーマット(RTL)のEPUBを開いた時だけその動作をする
- 時計表示機能を追加
  - 磁石で貼り付けることができるので作業時の時計表示に使えるな、と実装
  - [Settings]-[Reader]-[Customize Status Bar]の[Clock UTC Offset]を「UTC+9:00」とすることで日本時間表示に
- テスト用EPUBファイルにて動作を確認
  - 一部、特殊なフォントを必要とする文字以外について表示できることが期待される
- ルビ表示について対応中
  - 横書きであればルビに対応してるなら縦書きでも対応しておくかな、って

## 2026/08/29までの実装内容まとめ by claude code

ブランチ `feat/vertical-1.6`。本家タグ `1.6.0rc`（`6a501bba`）を起点に、旧ツリー
（`feat/vertical-writing-foundation`、1.5.0世代ベース）の成果を選別して再構成したもの。
旧ツリーが個別にcherry-pickしていた本家修正（#3071 CJKリスト高速化、#3034 ファイル一覧の
レース修正、#3026 SDフォールバック一括warm、#3001 EPUBメタデータの名前空間対応）は
1.6.0rcに全て含まれているため、移植対象から除外した。

### 診断基盤（INPUT_DIAG）の実装
- 目的: 動作の遅さや不具合を「体感で遅い」という主観の表現で扱うのではなく、
  ページめくりの所要ミリ秒やヒープ残量といった実測値として定量的に記録し、
  修正前後の比較や原因の切り分けを数値で行えるようにするため作成
- シリアルコンソールが使えないX3向けの、SDカードへ書き出す入力・描画計測
  （`/input-diag.txt`、`src/util/InputDiag.*`、`-diag`ビルド命名の`scripts/ost_version.py`）
- 1.6系開発時に追加: プリウォーム経路の計測（`page_scan_last`/`prewarm_entry_fails`）と、
  本を開く6段階のヒープ記録（`/open-heap.txt`。クラッシュしても直前までの段階が残る）

### 描画が返らなくなったときの自動再起動（開発ビルド専用、`DEBUG_RENDER_WATCHDOG`）
- 動機: 描画タスクが戻らなくなると端末を復帰させる手段が無い。描画タスクはどのウォッチドッグにも
  登録されておらず、CPU0のアイドルタスクも監視対象外（`sdkconfig.default`で
  `CONFIG_ESP_TASK_WDT_CHECK_IDLE_TASK_CPU0`が未設定）、電源断の判断は止まった描画に
  食われている`loop()`側にある。リセットボタンは接着された画面の下にあって押せない。
  結果として電池を空にするしか手が無く、それに1日以上かかる
- 対策: 描画の間だけ描画タスクをタスクウォッチドッグに登録し、30秒返らなければパニック再起動させる。
  待機中（通知待ち）は登録しないので、何もしていない端末で発火することはない。
  監視区間には描画ロックの待ちも含まれる——既に固まった描画が握っているのがそのロックだから
- 30秒という緩さは意図的で、「遅い」と「返らない」を区別できれば十分。実測の最大は時計の初回描画
  3.2秒、低速描画記録に残る最大が画像混在ページの5.6秒
- 旧ツリー（`develop`/`feat/vertical-writing-foundation`）の`c8318eae`を`feat/vertical-1.6`へ移植したもの。
  **2026-08-27に時計モードが約19分でハングして放電待ちになった直接の原因は、フラグを渡していても
  このブランチに実装自体が載っていなかったこと**——`#ifdef`なのでエラーも警告も出ずに素通りしていた
- 実機検証（2026-08-28〜29、下の電池測定と同一セッション）: 9時間16分・描画567回で誤発火ゼロ、
  uptime連続を確認

### メモリ断片化・クラッシュ対策
- グリフ用アドバンステーブルの収集バッファを16KB一括確保から256件開始の倍々成長に変更
  （断片化ヒープでの章ジャンプ7〜12秒/クラッシュの原因だった）
- グリフビットマップのミニアリーナを4KBチャンク分割確保に変更
  （本家未マージの`feat-chunk-bitmaps`由来。最大連続5KBの環境でもプリウォームが成立する）
- リスト画面（章選択・ブックマーク等）を開いた時点で全SDフォントキャッシュを解放
  （読書フォントの常駐数十KBを返してから章ジャンプの構築が走る）
- ページ読み込み前の低ヒープガード: ビルド進行中に空き20KB未満なら`suspendBuild()`で
  構築を部分ファイルとして退避（既存の遅延再開機構が引き継ぐ）、12KB未満でフォントキャッシュ解放

### 電書連 EPUB 3 制作ガイド準拠CSSによるメモリ枯渇の解消（JP版 #103/#105/#106 の移植）
- 電書連 EPUB 3 制作ガイド準拠CSS（実測144KB・約1,865ルール）が構築時に丸ごとRAM展開されて
  ヒープを食い尽くし、`-fno-exceptions`下の`bad_alloc`→`abort()`で再起動する問題への対策
- `CssSelectorUsage`: 章のHTMLを走査して使用タグ/クラス集合を作り、マッチするルールだけを
  RAMにロード。`Epub::load`のキャッシュ検証もヘッダのみの`validateCache()`に変更
- CSSパース中の32KBヒープガード3箇所と、打ち切られた不完全ルール集合をキャッシュに
  保存しない対策（オリジナルはJP版 zrn-ns氏）
- 効果（実測）: 構築の消費 約95KB→約24KB、読書中の空きヒープ 15KB→74〜90KB、クラッシュ解消

### 縦書き（tategaki）コアの移植
- UAX#50準拠の文字向き分類・縦書き句読点配置・禁則処理（`VerticalTextUtils.h`）
- 縦組版エンジン（`layoutVerticalColumns`: 右→左の列組み、列境界の禁則押し戻し、
  1〜2桁数字の縦中横、`3.14`等の数値非分断、Latin語の横倒し、語間スペースの保持）
- 縦書き描画（`renderVertical`: セル配置、`Sideways90CW`回転描画、ルビの計測・配置・描画）
- 縦書き判定: spineの`page-progression-direction="rtl"`かつCJK言語で自動有効
- ページ送り方向の反転（ボタン・タップゾーン・スワイプすべてRTL準拠）
- キャッシュ形式: `SECTION_FILE_VERSION` 39→40、`BOOK_CACHE_VERSION` 10→11
- rc側で進んでいた #2892（フォーカス分割の新データモデル）、#3001、#3025（リーダー統合）、
  スワイプ操作に適応する手移植（機械的なcherry-pickは不可能だった）

### 時計表示機能（clock mode）の作成
- Homeメニューに「Start clock mode」を追加。大きなデジタル時計を全画面表示し、
  Backボタンでhomeに戻る
- X3はスリープ中のタイマー起床ができない（GPIO13が電池側の電源を切る設計）ため、
  時計は常駐型: 自動スリープを止めたまま、待機中はCPUを10MHzまで落として消費を抑える
  （自動スリープ禁止とCPU全速の要否を分離する`needsFullSpeed()`を導入）
- 画面更新は毎分の部分書き換え＋30分ごとの残像取り（実測: 分更新 約445ms、残像取り 約3.2秒）
- 電池消費の記録機能: 時計モードの開始時と終了時に残量%・電圧mVをSDカードの
  `/clock-battery.txt`へ書き出し、終了時に1時間あたりの消費レートを自動計算する
- 電池の減り方（実測、2026-08-21）: 一晩12時間40分の連続表示で74%→55%、
  **約1.4%/h**（電圧では-10mV/h）。満充電からの連続時計表示は**約71時間（丸3日）**の見積もり。
  一晩の稼働でヒープ変動なし（リークなし）、毎分1回の描画をrender_count実測で確認済み
- **1.6.0rcベースへの移植後、再測定（2026-08-23）でも同水準を確認**: 12時間3分の連続表示で
  98%→79%、**約1.5%/h**（電圧では-14mV/h）。1回目の測定と近い値で再現性を確認
- **3回目の測定（2026-08-28〜29、`crosspoint-OST-2026082802-diag.bin`）**: 9時間16分の連続表示で
  100%→98%、電圧では4313mV→4146mV（**-18mV/h**）。残量%では-0.2%/hだが、これは満充電直後の
  平坦な領域だけを測ったためで、**この回の%/hを稼働時間に外挿してはいけない**——2回目の測定は
  ほぼ同じ電圧低下（-169mV）で残量表示が19%動いており、残量%は電圧に対して線形ではない。
  **比較できるのは電圧の方**で、-18mV/hは過去2回（-10・-14mV/h）と同水準。満充電から
  約60〜70時間という見積もりは据え置き
- 同セッションの健全性（9時間16分）: 空きヒープ76,124バイト・最小73,500バイトで差は2.6KB＝リークなし、
  描画567回＝毎分1回、ボタン確定19/19で取りこぼしゼロ、描画は初回3.2秒（残像取り）以降445ms一定で
  グリフ再構築0回
- **4回目の測定（2026-08-30、画像対応一式を積んだ後のビルド）**: 9時間47分で99%→96%、
  **-14mV/h**——2回目と同値で従来範囲（-10〜-18）の中央。ストリーミングPNGデコーダ・
  構築時事前生成・#3222・断片化ガード群のいずれも待機消費に影響なしを確認
- [Customize Status Bar]の「Clock Format」設定を時計にも反映（2026-08-23、実機確認済み）:
  24時間設定は従来どおり「HH:MM」、12時間設定では「H:MM」（先頭ゼロなし）に加えて
  単機能液晶の要領でAM/PMを上下2段のスロットに表示する（午前=上段・数字の上端揃え、
  午後=下段・数字の基線揃え）

### 本家修正の追加取り込み（#3009/#3122/#3134、いずれも実機確認済み）
- #3009: スリープ復帰時に前のスリープ画像が画面に残らないようクリア
- #3122: 実体参照の変換表に &amp;apos; を追加（章の表示では解析器が先に解決するため、
  効くのは変換表を直接引く別経路。検証の過程で、章XHTMLの名前付き実体はDOCTYPE宣言に
  DTD指定があるときだけ変換表で解決される、という処理経路の全体像も確定した）
- #3134: 章ファイルの &lt;/html&gt; 閉じタグより後に残っているゴミデータを無視
  （修正前は章全体が解析エラーで表示不能になる）

### 電源ボタンのスリープ復帰を改善（本家#3191の取り込み、実機確認済み）
- 復帰の判定方法が変わった。従来は設定の長押し時間だけ押し続けたかを計測していたが、
  入力のチャタリング除去が終わる前後で電源ピンの状態を直接見る方式になり、
  **復帰に長押しが不要**になった。実機で起動がスムーズになったことを確認
- 判定の位置がSDカードや設定ファイルを読む前まで前倒しされた。鞄の中で誤って
  押された場合も、カードに触らずにスリープへ戻る
- 本家のコード自身が残していた「単発のタップを2回続けると電源が入ってしまうことがある」
  という未解決の注記も、旧経路ごと解消された
- 起動時のUSBシリアル待ち250msが開発ビルド限定になった。X3はUSB書き込みロック品で
  シリアルコンソールが使えないため、実害なく起動が速くなる
- リカバリー起動（電源＋左側面上ボタン）は、従来の500msの待ち時間を挟まず
  チャタリング除去の直後に判定する形に変わった
- 新しい判定にはSDK側の新機能が必要なため、`freeink-sdk` を本家と同じ地点まで進めた
  （26コミット分、こちら側の独自変更は無し）。この範囲にはグレースケール描画の
  面反転バグ修正・一覧描画の範囲外アクセス修正・Wi-Fi認証情報の解析がメモリ逼迫時に
  落ちる問題の修正も含まれる

- `test/epubs-ja/vertical-test-suite.epub`: 開発中に作った診断用EPUBを
  1冊に統合して恒久資産化したもの。**現在15テスト・30章構成**（OPF名前空間接頭辞・
  段落配置と字下げ・半角記号の縦書き位置・全角スペース字下げ・実体参照2経路・
  閉じタグ後のゴミデータ・文字様記号/強調記号/異体字選択子・補助面漢字・CJK互換漢字/記号・
  傍点・全角空白の字下げと段落配置・縦書きの欧文語間空白・小書き仮名の縦書き位置・
  長大段落と中間区切りの耐性・約物の連続と行頭行末の括弧）。各テストの前に「どこを見て合否を判断するか」の日本語解説ページが
  入っており、実機で開くだけで判定できる。**章題は「テストN 解説/本文: ～」の形**——
  1つのテストが解説と本文の2章で構成されるため、番号の単位を「章」ではなく「テスト」にしてある
  （章選択画面に同じ番号が2行並ぶのを避け、対であることが読み取れる）。
  画像テスト書は9章それぞれが独立しているので「第N章」のまま。
  詳細は `test/epubs-ja/README` 参照
- **他フォークの終了済みPR/issueから要件を取り込み（2026-08-31、テスト4件追加）**:

    縦書きで段落配置を中央/右にすると字下げだけが消える不整合（Yomuka #20・抹茶 #163）
  - 第12章: 縦書きで欧文の語間空白が落ちて `Doyouseetheboy` になる（Yomuka #11）
  - 第13章: 小書き仮名が横組み字形のまま左下に沈む（JP版 #98）。**規格の出典はJLREQ 2.1.2の注1**で、

  - 第14章: 段落タグを持たず改行だけで区切られた数千字の長大段落での落ち（JP版 #74）、

    （Yomuka #10）——1章に集約した負荷試験。使う漢字1300字は**3書体すべてに実グリフが

  - 第15章（2026-08-31追加）: 約物が連続する場合の空きの取り方と、行頭・行末の括弧（JLREQ 3.1.4/3.1.5/
    3.1.9・行頭禁則・行末禁則）。会話文の多い小説で毎ページ現れる形で、他フォーク由来ではなく
    JLREQを直接読んで作った
  - 第14章の解説にルビのはみ出し処理の判定基準を追記（JLREQ 3.3.8）。仮名・長音記号・小書き仮名・

    隣の列と重なったら不合格、という形に落とした（READMEの「行分割時のルビ配分」未解決課題に対応する観点）
  - 画像テスト書は第8章の解説に、外字判定が書体で変わった前例（Yomuka #22）を受けて
    「ゴシック系と明朝系の両方で確認する」観点を明記。全9章も番号入りの章題に統一
  - **画像テスト書のmax-指定の出題は成立していなかった**（2026-08-31に修正）。

### 生成するフォントの仕様（OST版フォント fonts-YYYYMMDD<連番>.zip）
リリースに添付しているSDカード用日本語フォントは、`feat/japanese-sd-fonts`ブランチの
生成スクリプトで元フォントから自前変換したもの。BIZUDGothic / BIZUDMincho / NotoSansJP の
3書体×6サイズ（8/10ptはUI用、12〜18ptが読書用）、いずれもregular+boldの実体収録
（太字を斜め重ね打ちなどで合成せず、元フォントの太字から生成している）。
配置は `/fonts/<書体名>/<書体名>_<サイズ>.cpfont`。

収録範囲は「日本語の書籍に実際に出てくる字を、元フォントに実在する字形だけで持つ」という
方針で策定している:

- **漢字はJIS X 0213で絞り込む**。CJK統合漢字ブロック（約2.1万字）を丸ごと収録すると、
  日本語の書籍にはまず出てこない簡体字などで容量と機器側の区間管理を圧迫する。
  日本の出版物の漢字はJIS X 0213（約1.4万字分の符号位置リスト）で実質すべて賄えるため、
  ブロック単位ではなく符号位置リストで選別する
- **JIS X 0213の記号行を漏らさない**。丸数字①〜㊿・㈱・㎝㎏などはUnicodeブロックとしては
  漢字と別の場所に散らばっており、漢字リストだけでは拾えない。実機で○数字が化けた実例を
  受けて、囲みCJK・CJK互換（単位）・漢文記号・アイヌ語表記用の小書きカナなどの
  ブロックを明示的に加えている
- **引用・理系表記に備えた文字を持つ**。JIS X 0208由来のギリシャ・キリル文字
  （ロシア語等の引用）、数学記号・矢印・罫線・幾何図形などの記号ブロック。
  元フォントに無い字（∼ ≈ など）はNoto Sans / Noto Sans Mathを後詰めにして補う
- **縦書き用句読点（U+FE10〜、2026-08-22追加）**。縦書きで「、。，」を正しい位置・字形で
  描くための文字。NotoSansJPは収録字形を直接、BIZ UD系はフォント内部の縦書き用代替字形を
  取り出して収録する
- **実在する字形だけを数える**。収録候補は必ず元フォントの対応表と突き合わせ、
  字形の無い符号位置は落とす（「範囲は宣言してあるが中身は空」という字を作らない）。
  なお機器側の制約で区間表は最大256区間に隙間統合されるため、区間表上の公称字数は
  実体より大きく見える（例: BIZ UD系は公称約2.1万字・実体約1.2万字）

参考として、同系統のYomuka版フォント（Yomuka版が配布する変換済みフォント集）と
収録範囲を実グリフベースで比較した（2026-08-23）。かな・JIS漢字・基本記号は完全に共通で、
Yomuka版だけにある字はほぼ簡体字群（日本語書籍には実質不要）、逆に丸数字㉑〜㊿・㈱・
単位記号・キリル文字・縦書き用句読点などはOST版だけが持つ。ファイル形式も異なり
（OST版=v4・太字あり、Yomuka版=v5・太字なし）相互利用はできない。

### 同一起動内で本を開き直すとメモリ不足で落ちる問題の対策（実機確認済み）
- 読書フォントのキャッシュは本を閉じても保持される設計のため、同じ電源投入中に
  本を開いて閉じて別の本を開くと、2冊目は初回より約60KB不利な状態から始まる。
  CSSの重い本＋アンチエイリアスONの組み合わせでは足りなくなり、字形情報の確保が
  次々失敗（1KBの確保すら失敗）→ページ描画16秒→最終的に再起動、という実クラッシュが発生した
- 対策: 本を開く処理の冒頭で、空きが60KB未満（または最大連続40KB未満）なら
  フォントキャッシュを返してから開くようにした。開き直しが健全な初回と同じ条件になり、
  代償は開き直し直後1〜2ページの再読み込みのみ。クラッシュした再現手順で
  正常動作（空き72KBで開始・通常速度・クラッシュなし）を実機確認
- あわせて「本を閉じた時にどれだけメモリが戻ったか」の計測を診断に追加。初計測で
  「閉じて戻るのは約1KBだけ＝開くコストのほぼ全てはフォントキャッシュと固定インフラ」
  という実態も判明した

### 傍点（圏点）の表示（実機検証済み＝テスト第10章合格）
- CSSの `text-emphasis` / `text-emphasis-style`（`-epub-`/`-webkit-` 付きも含む6綴り）を解釈し、
  胡麻点・白胡麻点・点・丸・白丸・三角・二重丸の各字形で傍点を描く
- 描画はルビと同じ経路に載せた。縦書きは1文字＝1マスなので1マスに1つの印がそのまま対応する。
  横書きは1単語が1つの塊なので、印の後ろに全角スペースを挟んで文字数と幅を合わせている
- 同じ範囲にルビと傍点の両方が指定されたときはルビが勝つ。子孫要素の `none` は祖先の指定を
  打ち消す（下線などの装飾とは逆の挙動で、CSS本来の仕様どおり）
- 胡麻点（﹅ ﹆）は読書フォントに収録が無いことがあるため、収録の有無を実測して
  無ければ点（• ◦）に置き換える。フォントを更新すれば自動で本来の字形に戻る
- **縦書きで連続する欧文は1つのマスにまとめて横倒しにするため、`ABC` のような並びには
  印が1つしか付かない**（`X3` のような縦中横も1マス＝1つ）。日本語の文字には1つずつ付く

### 縦書き用記号のBIZ UD系での欠落を解消（実機検証済み＝テスト第9章合格）
- BIZ UD系は ︱︽︾ などを直接持たないため、これらを収録できていなかった
  （NotoSansJPのみ表示できる状態だった）。フォント内部の縦書き置換先の字形を取り出す
  既存の仕組みに原字の対応を17件追加し、互換形の実用範囲 U+FE30〜FE46 をまとめて収録範囲に指定
- 区間表は最大256区間に隙間統合されるため、︱ を足すと結果的に U+FE10〜FE46 が1区間になる。
  その内側を空宣言のままにせず実字形で埋める形にした（BIZ UD系で実字形0字→20字）
- 縦書き括弧 ︵〜﹄ の行頭・行末禁則も追加
- 収録できないのは ︲（BIZ UD系に縦書き用の字形が無い）と ︳︴（原字が同じ＿で直線形と
  波形を区別できない）の3字のみ

### 読書フォントに無いCJK互換漢字を統合漢字で描く（実機検証済み＝テスト第9章合格）
- 出版社の組版システムは字体を指定するためにCJK互換漢字（U+F900〜FAFF）を使うことがあるが、
  書体側にその字体が無いと豆腐になる。実際 BIZ UD系は 蓮 U+F999 は持つが
  溺 U+F9EC・煉 U+F993 を持たず、商業EPUB調査で見つけた3字のうち2字が表示できなかった
- 互換漢字と統合漢字は同じ字なので、読書フォントに字形が無いときだけ統合漢字の符号位置に
  置き換えて描くようにした。どちらもUTF-8で3バイトなので文字列をその場で書き換えられる。
  縦書き・横書きの共通経路に置いてあるため両方に効く
- 対応表は512要素の16bit配列（フラッシュ1KB、RAM消費なし）。有効なのは453字

### 画像のmax-width/max-height対応と列はみ出しの解消（2026-08-31、実機検証済み）
- **max-width/max-heightがCSSパーサに存在しなかった**。`width`/`height`しか解釈しないため、
  上限指定のある画像はすべて「コンテナに収める」既定動作に落ち、40%指定と100%指定が
  同じ大きさで描かれていた。**955冊調査で「市販の縦書き本の挿絵はほぼ全てmax-*クラスで
  寸法指定、固定幅は皆無」と判明していた**のに実装が伴っておらず、つまり商業書籍の挿絵は
  一枚も著者の指定どおりに表示されていなかった
  - 解析・**CSSキャッシュへの往復**・寸法計算の3箇所に対応。当初は解析だけ実装して
    キャッシュの直列化を忘れ、指定が読み戻しで消えていた（`width`/`height`は往復に
    入っていたので効き、`max-`だけ効かない、という食い違いの正体）
  - `width`/`height`と違い**縮めるだけで拡大しない**ので、上限はコンテナに対する下限として
    適用する。上限より小さい画像は原寸のまま（実測: 240x160の画像はmw=512*でも240x160）
  - 実機実測: 同じ560x760の画像が max-100%で512x694、**max-40%で205x278**
  - SECTION_FILE_VERSION 48、CSS_CACHE_VERSION 11
- **空白を含まない長い欧文が列を突き抜ける問題を解消**。解析器は連続ASCIIを1トークンに
  まとめるが、横倒しトークンの列方向の高さは語の幅そのもの。列より長い1トークンは
  トークン間でしか分割できないため、列の先頭から下へ突き抜けてステータスバーを侵食していた
  （2026-08-29のdiagにある`!! Outside range`論理y=855の正体）。文字境界の分かる解析段階で
  列に収まる大きさに分割し、レイアウト側にも保険の分岐を置いた。等幅系とゴシック系で
  分割位置が変わることを実機確認——実測した文字送り幅で判定している証拠。SECTION_FILE_VERSION 47
- **診断の強化**: 画像1枚ごとに`fit mw=N* mh=N*`（星は著者が指定した上限）を記録。
  写真の見比べでは6往復しても決着しなかったmax-指定の可否が、この1行で確定した。
  あわせて画像診断のリングを24→48件に拡張（10枚の章で約50行書かれ、
  肝心の先頭が溢れて2回続けて必要な行が取れなかったため）

### 縦書き組版の規格準拠2件とAAの適応的な見送り（2026-08-31、実機検証済み）
新テスト（テスト11〜15）が見つけた不具合を修正した。いずれも他フォークが実書で
報告していたもので、こちらのツリーにも同じ形で存在することが実機で確認された。
- **全角空白による字下げの二重適用**（Yomuka版 #21相当）: 文庫系EPUBは行頭の字下げを
  全角空白（U+3000）そのもので書く。読み手側の自動字下げが重ねて効くと2文字分空く。
  段落の先頭が全角空白のときは自動字下げを見送る方式に変更（市販の読書アプリと同じ挙動）。
  `beginsWithIdeographicSpace()`を1箇所に置き縦横両経路から使うことで、両者が食い違わない形にした。
  **CSSの`text-indent`明示は従来どおり優先**。SECTION_FILE_VERSION 45→46
  - **注意: この修正はExtra Paragraph SpacingがOFFのときだけ効く**。ONだと自動字下げ自体が
    無効なので二重字下げも起こらない。既定値はONなので、既定のまま使う限り影響はない
- **小書き仮名の縦書き位置**（JP版 #98相当）: 「ぁぃゃゅょっ」等の字面は、JLREQ 2.1.2の注1で
  縦組みでは「文字の外枠の**天地中央で右寄り**」と定められている。フォントは横組み用の
  位置を持つため、そのまま使うと列の軸から外れて見える。マス目幅の1/8だけ右へ寄せる方式で対応。
  **上下は動かさない**——JP版の実装は右かつ上へ動かし出典も3.1.4（実際は約物連続の節）と
  しているが、規格に当たると上げる根拠はない。送り幅は不変なので列の折り返し・ルビ・行間に影響なし
- **常駐できないページのAA見送り**: 白黒描画の1回で字形のオンデマンド読みが64回を超えたら、
  滑らかな描画（同じ描画を約20回繰り返す工程）を行わない。1回目のコストが確定した時点で
  20倍になることが分かるため、推測ではなく実測による打ち切り。既存の「作業領域が取れなければ
  AAを諦める」経路の隣に置いた。実測: 最悪描画 27,030ms→3,998ms、1描画のオンデマンド読み
  1,755→106。通常ページではAAは従来どおり動作（gray_lsb/gray_msbが非ゼロ）＝誤発動なし
