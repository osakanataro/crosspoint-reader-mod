# CrossPoint Reader OST 改造版

XTEINK X3上で日本語EPUBファイルを読むために、CrossPoint Reader を改造しています。
命名は面倒くさくなったのでOSakanaTaro版ってことでOST版です。

ブランチ `feat/vertical-1.6`。本家タグ `1.6.0rc`（`6a501bba`）を起点に、旧ツリー

### 診断基盤（INPUT_DIAG）の実装
- 目的: 動作の遅さや不具合を「体感で遅い」という主観の表現で扱うのではなく、
  ページめくりの所要ミリ秒やヒープ残量といった実測値として定量的に記録し、
  修正前後の比較や原因の切り分けを数値で行えるようにするため作成
- シリアルコンソールが使えないX3向けの、SDカードへ書き出す入力・描画計測
  （`/input-diag.txt`、`src/util/InputDiag.*`、`-diag`ビルド命名の`scripts/ost_version.py`）
- 1.6系開発時に追加: プリウォーム経路の計測（`page_scan_last`/`prewarm_entry_fails`）と、
  本を開く6段階のヒープ記録（`/open-heap.txt`。クラッシュしても直前までの段階が残る）

### メモリ断片化・クラッシュ対策
- グリフ用アドバンステーブルの収集バッファを16KB一括確保から256件開始の倍々成長に変更
  （断片化ヒープでの章ジャンプ7〜12秒/クラッシュの原因だった）
- グリフビットマップのミニアリーナを4KBチャンク分割確保に変更
  （本家未マージの`feat-chunk-bitmaps`由来。最大連続5KBの環境でもプリウォームが成立する）
- リスト画面（章選択・ブックマーク等）を開いた時点で全SDフォントキャッシュを解放
  （読書フォントの常駐数十KBを返してから章ジャンプの構築が走る）
- ページ読み込み前の低ヒープガード: ビルド進行中に空き20KB未満なら`suspendBuild()`で
  構築を部分ファイルとして退避（既存の遅延再開機構が引き継ぐ）、12KB未満でフォントキャッシュ解放

### 電書連 EPUB 3 制作ガイド準拠CSSによるメモリ枯渇の解消（JP版 #103/#105/#106 の移植）
- 電書連 EPUB 3 制作ガイド準拠CSS（実測144KB・約1,865ルール）が構築時に丸ごとRAM展開されて
  ヒープを食い尽くし、`-fno-exceptions`下の`bad_alloc`→`abort()`で再起動する問題への対策
- `CssSelectorUsage`: 章のHTMLを走査して使用タグ/クラス集合を作り、マッチするルールだけを
  RAMにロード。`Epub::load`のキャッシュ検証もヘッダのみの`validateCache()`に変更
- CSSパース中の32KBヒープガード3箇所と、打ち切られた不完全ルール集合をキャッシュに
  保存しない対策（オリジナルはJP版 zrn-ns氏）
- 効果（実測）: 構築の消費 約95KB→約24KB、読書中の空きヒープ 15KB→74〜90KB、クラッシュ解消

### 縦書き（tategaki）コアの移植

- ページ送り方向の反転（ボタン・タップゾーン・スワイプすべてRTL準拠）

### 時計表示機能（clock mode）の作成
- Homeメニューに「Start clock mode」を追加。大きなデジタル時計を全画面表示し、
  Backボタンでhomeに戻る
- X3はスリープ中のタイマー起床ができない（GPIO13が電池側の電源を切る設計）ため、
  時計は常駐型: 自動スリープを止めたまま、待機中はCPUを10MHzまで落として消費を抑える
  （自動スリープ禁止とCPU全速の要否を分離する`needsFullSpeed()`を導入）
- 画面更新は毎分の部分書き換え＋30分ごとの残像取り（実測: 分更新 約445ms、残像取り 約3.2秒）
- 電池消費の記録機能: 時計モードの開始時と終了時に残量%・電圧mVをSDカードの
  `/clock-battery.txt`へ書き出し、終了時に1時間あたりの消費レートを自動計算する
- 電池の減り方（実測、2026-08-21）: 一晩12時間40分の連続表示で74%→55%、
  **約1.4%/h**（電圧では-10mV/h）。満充電からの連続時計表示は**約71時間（丸3日）**の見積もり。
  一晩の稼働でヒープ変動なし（リークなし）、毎分1回の描画をrender_count実測で確認済み
- **1.6.0rcベースへの移植後、再測定（2026-08-23）でも同水準を確認**: 12時間3分の連続表示で
  98%→79%、**約1.5%/h**（電圧では-14mV/h）。1回目の測定と近い値で再現性を確認
- [Customize Status Bar]の「Clock Format」設定を時計にも反映（2026-08-23、実機確認済み）:
  24時間設定は従来どおり「HH:MM」、12時間設定では「H:MM」（先頭ゼロなし）に加えて
  単機能液晶の要領でAM/PMを上下2段のスロットに表示する（午前=上段・数字の上端揃え、
  午後=下段・数字の基線揃え）

### 本家#3107の取り込み（グリフ事前読み込みの不発を解消）
- SDフォントのフォントIDはハッシュ由来で負の値になり得るが、ページ走査テーブルが「-1＝空き」の
  判定を使っていたため、走査で集めた文字集合が事前読み込みされずに捨てられていた——という
  本家の修正（2026-08-19）をcherry-pick。診断基盤で追っていた「走査は全量集めるのに
  事前読み込みが9msで何もしない」「ページ描画中にグリフを1ページ1367回SDから読み直す」の
  原因そのものだった
- 効果（実測、同一書籍・同一条件の前後比較）:
  - ページ送り 約1.3〜1.6秒 → **約0.7〜0.9秒**（従来の「正常」も実は事前読み込み不発だった）
  - 連打ページ送りで6回目以降から遅くなる現象が解消
  - アンチエイリアスON時 1ページ15〜21秒 → 1.1〜4.9秒（壊滅的だったものが実用域に）
  - ページ描画中のSDからのグリフ個別読み 1367回 → 0回

### 縦書きでの章内画像の調査（表示対応の実装自体は保留）
- 画像混在テストEPUB（`test/epubs-ja/vertical-image-test.epub`、インライン・挿絵・全画面・
  外字1em角・低ビット深度PNGの5章構成）を作成し、診断基盤に画像処理トレース
  （`/image-diag.txt`。画像1枚ごとに発見→寸法取得→配置/代替テキスト、描画時の展開→デコードの
  成否と、その瞬間のヒープを記録）を追加して切り分けた
- 結論: X3の章内画像は参照パス・画像形式・サイズではなく**連続メモリの二段の壁**で決まる。
  (1) 圧縮格納されたzipエントリの読み出しは約32KBの展開用窓を要求、
  (2) PNGデコーダは内部に約60KBを一括で抱える設計。日本語フォント常駐＋縦書き構築中の
  最大連続12〜28KBではどちらも越えられず、構築時は代替テキストに、描画時は空の枠になる
  （枠は横書き用の座標のまま置かれ本文に重なる、という縦書き配置の未実装も併発）
- 画像を無圧縮格納にすると第1の壁は消えることを実証（実際のEPUBは通常、画像を無圧縮格納する）
- 対応方針はヒープが空いている構築時にピクセルキャッシュを事前生成する方式（Yomuka版が
  同方式を実装済み）が本命と判断し、今回はここまでで保留

### 句読点を縦書き用の字形で描画（フォント再生成込み、実機確認済み）
- 従来は横書き用の「、。，」の字形を右上へ半マスずらして置く近似だったが、
  Unicodeの縦書き用句読点（︑U+FE11・︒U+FE12・︐U+FE10）を使う方式に変更。
  SDフォント生成スクリプトに縦書き用字形の抽出を実装し（NotoSansJPは直接収録、
  BIZ UD系はフォント内の縦書き置換先の字形を取り出して収録）、3書体×6サイズを再生成
- 縦書きの組版時に、読書フォントがこれらの字形を持っていれば「、。，」を置き換える。
  持っていない旧フォントではずらし近似のまま動く（新旧どの組み合わせでも壊れない）
- **この改善にはリリース添付のフォント（fonts-20260822.zip以降、現行はfonts-20260826.zip）への差し替えが必要**
  （zip内は`fonts/`直下構成でSDへそのまま展開できる）。全角ピリオド「．」だけは
  縦書き用の符号位置がUnicodeに無いため従来のずらし近似のまま

### 生成するフォントの仕様（OST版フォント fonts-YYYYMMDD<連番>.zip）
リリースに添付しているSDカード用日本語フォントは、`feat/japanese-sd-fonts`ブランチの
生成スクリプトで元フォントから自前変換したもの。BIZUDGothic / BIZUDMincho / NotoSansJP の
3書体×6サイズ（8/10ptはUI用、12〜18ptが読書用）、いずれもregular+boldの実体収録
（太字を斜め重ね打ちなどで合成せず、元フォントの太字から生成している）。
配置は `/fonts/<書体名>/<書体名>_<サイズ>.cpfont`。

収録範囲は「日本語の書籍に実際に出てくる字を、元フォントに実在する字形だけで持つ」という
方針で策定している:

- **漢字はJIS X 0213で絞り込む**。CJK統合漢字ブロック（約2.1万字）を丸ごと収録すると、
  日本語の書籍にはまず出てこない簡体字などで容量と機器側の区間管理を圧迫する。
  日本の出版物の漢字はJIS X 0213（約1.4万字分の符号位置リスト）で実質すべて賄えるため、
  ブロック単位ではなく符号位置リストで選別する
- **JIS X 0213の記号行を漏らさない**。丸数字①〜㊿・㈱・㎝㎏などはUnicodeブロックとしては
  漢字と別の場所に散らばっており、漢字リストだけでは拾えない。実機で○数字が化けた実例を
  受けて、囲みCJK・CJK互換（単位）・漢文記号・アイヌ語表記用の小書きカナなどの
  ブロックを明示的に加えている
- **引用・理系表記に備えた文字を持つ**。JIS X 0208由来のギリシャ・キリル文字
  （ロシア語等の引用）、数学記号・矢印・罫線・幾何図形などの記号ブロック。
  元フォントに無い字（∼ ≈ など）はNoto Sans / Noto Sans Mathを後詰めにして補う
- **縦書き用句読点（U+FE10〜、2026-08-22追加）**。縦書きで「、。，」を正しい位置・字形で
  描くための文字。NotoSansJPは収録字形を直接、BIZ UD系はフォント内部の縦書き用代替字形を
  取り出して収録する
- **実在する字形だけを数える**。収録候補は必ず元フォントの対応表と突き合わせ、
  字形の無い符号位置は落とす（「範囲は宣言してあるが中身は空」という字を作らない）。
  なお機器側の制約で区間表は最大256区間に隙間統合されるため、区間表上の公称字数は
  実体より大きく見える（例: BIZ UD系は公称約2.1万字・実体約1.2万字）

参考として、同系統のYomuka版フォント（Yomuka版が配布する変換済みフォント集）と
収録範囲を実グリフベースで比較した（2026-08-23）。かな・JIS漢字・基本記号は完全に共通で、
Yomuka版だけにある字はほぼ簡体字群（日本語書籍には実質不要）、逆に丸数字㉑〜㊿・㈱・
単位記号・キリル文字・縦書き用句読点などはOST版だけが持つ。ファイル形式も異なり
（OST版=v4・太字あり、Yomuka版=v5・太字なし）相互利用はできない。

### 章を開けなくなる「Failed to index」の対策（実機確認済み）
- 実機ログで原因を特定: 章本文をzipから取り出すには約32KBの連続した空きメモリが要るが、
  ルビや珍しい漢字の多い本を読み進めると空きが細切れになり、合計では足りていても
  連続では取れず3回連続で失敗→「Failed to index」になっていた。既存の保護は
  空き合計しか見ておらず、この断片化を見逃していた
- 章本文の取り出し直前と再試行時に「最大連続48KB未満ならフォントの確保済み領域を
  返してから実行」する保護を追加。再現していた本で全章のページ送りが通ることを確認

### 同一起動内で本を開き直すとメモリ不足で落ちる問題の対策（実機確認済み）
- 読書フォントのキャッシュは本を閉じても保持される設計のため、同じ電源投入中に
  本を開いて閉じて別の本を開くと、2冊目は初回より約60KB不利な状態から始まる。
  CSSの重い本＋アンチエイリアスONの組み合わせでは足りなくなり、字形情報の確保が
  次々失敗（1KBの確保すら失敗）→ページ描画16秒→最終的に再起動、という実クラッシュが発生した
- 対策: 本を開く処理の冒頭で、空きが60KB未満（または最大連続40KB未満）なら
  フォントキャッシュを返してから開くようにした。開き直しが健全な初回と同じ条件になり、
  代償は開き直し直後1〜2ページの再読み込みのみ。クラッシュした再現手順で
  正常動作（空き72KBで開始・通常速度・クラッシュなし）を実機確認
- あわせて「本を閉じた時にどれだけメモリが戻ったか」の計測を診断に追加。初計測で
  「閉じて戻るのは約1KBだけ＝開くコストのほぼ全てはフォントキャッシュと固定インフラ」
  という実態も判明した

### 英数字だけの段落の表示位置修正（実機確認済み）
- 英文だけで1列が埋まると、全角マスの幅を列の中から求められず行の高さで代用しており、
  その列だけ本文が右にずれ、日本語ルビが右隣の列に食い込んでいた
  （NotoSansJP 18ptの実測でルビ右端81px＞列送り67px）
- 組版時に決めた全角マス幅を列データに持たせて描画で使うよう変更。段落をまたいで
  直前の全角幅を引き継ぐため、英数字だけの段落でも周囲と同じマス幅で組まれる

### 実書籍の使用文字調査に基づくフォント収録拡張と表示修正（実機確認済み）
なろう・カクヨム取得の513冊と商業EPUB955冊の全本文を対象に、使用文字とフォント収録範囲を
突き合わせる調査を実施（商業書籍は使用文字の集計のみで本文は保存・引用していない）。
カバー率は文字種で95%超・出現回数ベースで99.99%超と高かったが、以下の実害を発見し修正した:

- **℃が収録されていなかった**（513冊中57冊で使用）。フォント生成の範囲設定に
  「文字様記号ブロック（℃・ℓ・№・Åなど）」がまるごと抜ける隙間があった。
  あわせて実データで見つかった⭐⬛⬇⌒⌘なども追加
- **異体字選択子（VS15/VS16）が本文中に四角として表示されていた**（のべ1,288回、
  最大1冊275回）。これは「直前の字を文字調で表示せよ」という見えない制御文字で、
  フォント収録の問題ではなく解析器が読み飛ばすべきもの。BOMと同じ扱いで修正
- **𠮟（しかる、JIS X 0213字体）の収録と縦書き正立**（6冊で使用）。Unicode補助面
  （4バイトUTF-8）の漢字で、フォント生成の範囲外だったのに加え、縦書きの正立判定も
  補助面を知らず横倒しに回転していた。両方修正し、今後の補助面漢字は
  リストファイルに1行追記するだけで収録できる設計にした
- **溺・蓮・煉（CJK互換漢字）の収録**（商業書籍で計18冊）。JIS X 0213許可リストが
  互換漢字の重複コードポイントを弾いていた。同じく追記で拡張できるリスト方式で対応
- **⦿と縦書き用記号︱︲︽︾の収録**。︱︽︾は最初から縦書き用に成形済みの字形のため、
  正立扱い＋《》と同じ行頭・行末禁則も追加
- 検証用に `test/epubs-ja/vertical-test-suite.epub` へ第7〜9章を追加（現在18章構成）。
  **この改善には fonts-20260826.zip 以降への差し替えが必要**

### 傍点（圏点）の表示（実機検証済み＝テスト第10章合格）
- CSSの `text-emphasis` / `text-emphasis-style`（`-epub-`/`-webkit-` 付きも含む6綴り）を解釈し、
  胡麻点・白胡麻点・点・丸・白丸・三角・二重丸の各字形で傍点を描く
- 描画はルビと同じ経路に載せた。縦書きは1文字＝1マスなので1マスに1つの印がそのまま対応する。
  横書きは1単語が1つの塊なので、印の後ろに全角スペースを挟んで文字数と幅を合わせている
- 同じ範囲にルビと傍点の両方が指定されたときはルビが勝つ。子孫要素の `none` は祖先の指定を
  打ち消す（下線などの装飾とは逆の挙動で、CSS本来の仕様どおり）
- 胡麻点（﹅ ﹆）は読書フォントに収録が無いことがあるため、収録の有無を実測して
  無ければ点（• ◦）に置き換える。フォントを更新すれば自動で本来の字形に戻る
- **縦書きで連続する欧文は1つのマスにまとめて横倒しにするため、`ABC` のような並びには
  印が1つしか付かない**（`X3` のような縦中横も1マス＝1つ）。日本語の文字には1つずつ付く

### 縦書き用記号のBIZ UD系での欠落を解消（実機検証済み＝テスト第9章合格）
- BIZ UD系は ︱︽︾ などを直接持たないため、これらを収録できていなかった
  （NotoSansJPのみ表示できる状態だった）。フォント内部の縦書き置換先の字形を取り出す
  既存の仕組みに原字の対応を17件追加し、互換形の実用範囲 U+FE30〜FE46 をまとめて収録範囲に指定
- 区間表は最大256区間に隙間統合されるため、︱ を足すと結果的に U+FE10〜FE46 が1区間になる。
  その内側を空宣言のままにせず実字形で埋める形にした（BIZ UD系で実字形0字→20字）
- 縦書き括弧 ︵〜﹄ の行頭・行末禁則も追加
- 収録できないのは ︲（BIZ UD系に縦書き用の字形が無い）と ︳︴（原字が同じ＿で直線形と
  波形を区別できない）の3字のみ

### 読書フォントに無いCJK互換漢字を統合漢字で描く（実機検証済み＝テスト第9章合格）
- 出版社の組版システムは字体を指定するためにCJK互換漢字（U+F900〜FAFF）を使うことがあるが、
  書体側にその字体が無いと豆腐になる。実際 BIZ UD系は 蓮 U+F999 は持つが
  溺 U+F9EC・煉 U+F993 を持たず、商業EPUB調査で見つけた3字のうち2字が表示できなかった
- 互換漢字と統合漢字は同じ字なので、読書フォントに字形が無いときだけ統合漢字の符号位置に
  置き換えて描くようにした。どちらもUTF-8で3バイトなので文字列をその場で書き換えられる。
  縦書き・横書きの共通経路に置いてあるため両方に効く
- 対応表は512要素の16bit配列（フラッシュ1KB、RAM消費なし）。有効なのは453字

### 実機での状態（X3、日本語SDフォント・自作の電書連 EPUB 3 制作ガイド準拠EPUB）
- 縦書き表示・ルビ・RTLページ送り動作、横書きの回帰なし
